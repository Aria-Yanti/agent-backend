# 项目说明 · Agent Playground — 审计智能体后端

> 本文件是作品集/面试专用说明，与 `README.md`（技术使用文档）互补：README 回答"这是什么、怎么跑"，本文回答"**为什么做、我怎么想、难点在哪**"。

---

## 1. 项目概述（30 秒版）

**做什么**：把财务报表审计中可标准化的程序性工作（分析、风险识别、计划、凭证核对、合同校验、函证、错报汇总、复核）编排为 8 个 AI Agent 接力执行的流水线，用**共享审计上下文 + 人工复核门**解决多 Agent 一致性和审计责任闭环问题。

**解决什么问题**：审计项目是"多角色接力 + 共享工作底稿 + 逐级复核"的典型协作场景。通用 Agent 框架（如 AutoGen、LangGraph 单机 demo）只解决"多模型对话"，不解决"多 Agent 共享一份可追溯的工作底稿"和"AI 结论如何进入审计师责任闭环"这两个垂直问题。

**技术栈**：FastAPI + LangGraph + OpenAI 兼容网关 + SQLite + JSON/JSONL 事件溯源 + 确定性规则引擎。

## 2. 我的角色与贡献

> 项目性质：**团队比赛作品**，本人为团队核心成员，参与整体架构设计与评审，并主要负责以下三个方向的实现与联调。

- **共享审计上下文机制**：参与版本化共享上下文协议的设计与实现——Agent 执行前读取最新 Audit.md，执行后写回并递增版本，通过事件溯源与 Markdown 投影保证多 Agent 底稿一致、结论可追溯。
- **执行层可靠性治理**：参与 LLM 工具调用循环的可靠性设计——证据冲突检测、失败分级降级、输出噪声清洗，以及无 API Key 场景的全链路 fallback，保证演示结果可复现。
- **多工作流体系搭建**：参与 6 种多 Agent 工作流（LangGraph 通用模式 + 审计顺序链）的架构设计与统一编译管线实现。

## 3. 背景与动机

审计实务中，收入确认（尤其期末集中确认、第三方代付）是重大错报高风险领域。传统工具（Excel、SQL、RPA）只能做**单点自动化**：

- 分析性程序、凭证核对、函证跟踪彼此割裂，数据口径不一致；
- 工作底稿散落在不同文件，无法回答"这条结论基于哪份证据、由哪个角色、在什么版本下写入"；
- AI 生成的结论没有进入审计责任链条——**没有人签字，就不算审计证据**。

本项目把这三个痛点作为设计约束：**上下文必须共享且可追溯，证据必须有来源，最终结论必须经过人**。

## 4. 技术选型与理由

| 决策 | 选择 | 备选 | 理由 |
|---|---|---|---|
| Web 框架 | FastAPI | Flask / Django | 原生 Pydantic 校验 + SSE 流式支持，前端实时追踪 Agent 执行过程 |
| 工作流编排 | LangGraph | 自研状态机 / AutoGen | 显式状态图 + 条件边，5 种通用模式复用同一编译管线；审计专用链保留手写实现以精确控制顺序与写回 |
| LLM 接入 | OpenAI 兼容接口 | 各家私有 SDK | 一套代码兼容官方与代理，实测部分代理对 tool 请求返回 400，故审计链剥离工具规避 |
| 审计上下文存储 | JSON 状态 + JSONL 事件 + Markdown 投影 | 单一数据库 | 三层各司其职：状态可快照、事件可审计、Markdown 是人和 Agent 共同可读的工作底稿 |
| 异常识别 | 确定性规则引擎 | 纯 LLM 判断 | 证据识别不允许幻觉：付款方一致性、授权文件、金额勾稽都是可复算的规则 |
| 演示能力 | 内置 A-101 样例包 + fallback | 依赖真实 API | 无 API Key 也能完整复现"5 笔异常 / ¥32M"结果，降低作品演示门槛 |

## 5. 核心技术难点与解决方案

### 难点 1：8 个 Agent 如何共享同一份审计上下文且不冲突？

**问题**：每个 Agent 独立调用 LLM，输出格式自由；若各自维护结论，就会出现"分析 Agent 看到的是 v3、复核 Agent 写的是 v5"的错位，且无法回答"某条结论在哪个版本引入"。

**方案**：三层上下文协议。
1. **状态层**：`AuditContextState`（JSON）保存风险登记册、证据索引、Agent 发现、错报汇总等结构化数据，维护单调递增的 `version`；
2. **事件层**：每次写回追加一条 JSONL 事件（`agent_patch_applied`，记录 `version_before → version_after`、`patch_keys`、actor）；
3. **投影层**：每次写回后重新渲染 `Audit.md`（Markdown）落盘——它既是 Agent 下一轮读取的"最新底稿"，也是人可读的工作文件。

**执行协议**（写死在顺序链中）：每个 Agent 执行前**必须读取最新 Audit.md 全文**，执行后**必须先把本节点摘要写入**再流转，禁止"先推进流程、后补写文件"。

**代码证据**：`app/audit_runtime/context_store.py:apply_patch`（版本递增 + 事件追加 + 重渲染）、`app/audit_runtime/agent_chain_executor.py`（顺序链协议）、`app/audit_runtime/audit_md_projection.py`（投影）。

**效果**：一次完整运行可看到 `v1（初始化）→ v9（复核写回）` 的版本演进，前端通过 SSE 实时收到每次写回。

---

### 难点 2：AI 结论如何进入审计责任闭环？

**问题**：AI 不能替审计师签字，但若把 AI 输出直接当结论，就绕过了审计准则要求的复核责任；若完全不采纳，Agent 流水线又失去意义。

**方案**：**人工复核门（HumanReviewGate）**——"半硬暂停"设计。
1. 复核 Agent 完成后，自动基于上下文生成一个结构化复核门（含 AI 推荐意见、证据引用、疑似错报金额、待答问题）；
2. 审计师通过 API 提交四种决定之一：`approved` / `need_more_evidence` / `rejected` / `escalated`；
3. 决定**写回审计轨迹**（`review_decisions` 事件，记录 reviewer、comment、版本前后），并驱动上下文 `version+1`；
4. 决定影响**信任评分**（复核完成率是四维评分之一）。

**"半硬"的含义**：复核门发布时流水线不中断（可继续到 Synthesizer 汇总），但上下文标记 `paused=true`，UI 可见"等待人工复核"状态——既不让 AI 自说自话收尾，也不阻塞演示流程。

**代码证据**：`app/audit_runtime/gate_helpers.py:build_final_review_gate`（门结构）、`context_store.py:register_review_gate / apply_gate_decision`（发布与决策）、`routes.py:post_audit_review_gate_decision`（API）。

**效果**：人机责任边界清晰——AI 负责"提示风险并给出建议"，审计师负责"做决定"，且每个决定都可审计。

---

### 难点 3：LLM 工具调用如何保证可靠、不产生幻觉？

**问题**：LLM 可能①编造工具结果，②把工具协议噪声（DSML 标签）泄漏进正文，③遇到上游代理 5xx 直接失败，④收敛不出最终答案却假装完成。

**方案**（按失败层级分级防御）：
1. **证据冲突检测**：工具调用完成后，若模型回答与工具证据矛盾（`action_json` 契约下），强制进入总结修复阶段（`_force_final_tool_answer`），不直接放行；
2. **噪声清洗**：输出解析器按规则删除 DSML/裸 `<tool_calls>`/"Let me…"前缀等泄漏（`output_parser.py:strip_tool_noise`），保证 Audit.md 不被污染；
3. **失败重试与降级**：上游瞬时错误退避重试 3 次；文件类错误（FILE_NOT_FOUND）可恢复则重试，不可恢复则移除该工具；最终仍无收敛时显式返回 `TOOL_EXECUTION_NO_FINAL_ANSWER` 标记，**禁止把失败伪装成成功**；
4. **全链路 fallback**：无 API Key 时路由/规划/Agent 执行全部走规则 fallback，演示模式仍可完整跑通。

**代码证据**：`app/runtime.py:_run_agent_with_tools`（工具循环 + 分级防御）、`_answer_conflicts_with_tool_evidence`、`output_parser.py`。

**效果**：演示模式下无真实 API 也能产出结构化结果；有 API 时工具结果与叙事可交叉验证。

---

### 难点 4：审计证据识别为什么必须用规则引擎？

**问题**：若让 LLM 直接判断"这笔收入是否异常"，模型可能给出似是而非的结论且**无法复算**——审计场景要求每个异常都能追溯到具体规则命中。

**方案**：**规则引擎 + LLM 分工**。
- **规则引擎**（确定性，可复算）：对 6 张 CSV（收入明细/银行回款/合同/发票/应收/预期结论）执行勾稽——付款方≠合同客户（+2 分）、合同未允许第三方代付（+2 分）、授权文件缺失（+2 分）、收入确认早于验收（+2 分）、期末窗口集中确认（+1 分）、金额无法勾稽（+1 分），按分值映射高中低风险，并产出结构化异常候选（含异常类型、证据引用、建议程序）；
- **LLM**（生成式）：基于规则输出撰写审计叙事、设计审计程序、输出复核建议。

**代码证据**：`app/audit_data/revenue_analyzer.py:analyze_a101_sample`（规则打分与候选生成）、`matching_engine.py`（与预期结论对比）。

**效果**：A-101 演示结果（5 笔异常 / ¥32,000,000）可由 `scripts/validate_a101_test_package.py` **一键复现**，每笔异常都能回答"命中哪些规则"。

## 7. 局限与后续方向（展示思考深度）

**当前局限（诚实清单）**：
1. 演示场景固定为 A-101（收入虚增——第三方代付），规则引擎尚未泛化到其他风险类型；
2. `audit_context/`（第一版）与 `audit_runtime/`（第二版）双上下文并存，新功能基于第二版，第一版待收敛；
3. 未做真实 API Key 下的长时间稳定性验证，生产配置（模型/代理）依赖 `.env`。

**后续方向**：
1. **场景泛化**：把规则引擎参数化（风险类型、重要性水平、异常规则可配置），支持多项目并行上下文；
2. **证据链自动化**：自动抓取合同/发票/回单等文件进入证据索引，减少手工占位文件；
3. **复核规则可配置化**：复核门的问题与阈值从配置读取，而非硬编码；
4. **质量工程**：把 `scripts/` 的散装验证整合为 pytest 套件，补 CI。
